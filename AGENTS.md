# Road Trip

Given a start and end location, a start and end time, and whether the trip is a round trip or one way, Road Trip lists events and activities along the road between the two points, for the dates and times of the trip. It is for people planning a drive who want to know what is on along the way. The look and the behaviour of the list follow the Montreal Weekend Board (the lifelike-and-believable/montreal-weekend-board repository).

## Commands

- Verify (run before reporting work as done, and include its output): `npm run verify`
- Dev server: `npm run dev` (check for one already running first)
- Live check against the real map and Claude services (not part of verify): `npm run live`; add `LIVE_SOURCES=1` to also find sources, or `LIVE_LISTINGS=1` to also read the first few places for events. Both spend money. Never run them unprompted.

## Project decisions

- Next.js 16, React, TypeScript, Node runtime on Vercel. No relational database until a feature needs one; record the choice here when it does.
- Input: start place, end place, start date and time, end date and time, and a one-way or round-trip choice. A round trip lists the outbound and return legs separately, and the return leg uses the return times.
- Output: events and activities near the route, grouped by day and ordered by time, so a listing is shown only if it falls inside the window in which the traveller is passing that part of the road.
- Style carried over from the Montreal Weekend Board: day sections that fold, category chips, a sticky filter bar, a star on each entry that means "I like this" without claiming attendance, a picks itinerary that reports the gap between consecutive picks, free-or-ticketed marking, and an installable PWA with safe-area handling for standalone mode.
- Where the Montreal board says only what it knows (it never invents a distance or journey time), Road Trip does the same. Show a detour or drive time only when a routing service supplied it, and label what it was supplied by.
- Trips are stored in Redis (Upstash, via Vercel Storage) as `trips/<id>`, reached over its REST interface with `fetch`, the way the Montreal board's store module does. Settings: `AUTH_SECRET`, `BOARD_PASSCODE` (one shared passcode and a signed cookie, named as in the Montreal board), `DOC_SALT`, `REFRESH_SECRET` (bearer token for a manual refresh) and `CRON_SECRET` (the token Vercel's scheduler sends; give it the same value as `REFRESH_SECRET`), `KV_REST_API_URL`, `KV_REST_API_TOKEN`, `ANTHROPIC_API_KEY`, `LISTINGS_BY` (`routine`, the default, or `cron`), and optionally `ANTHROPIC_MODEL` (default `claude-sonnet-5-5`; reasoning effort is pinned to medium in `src/lib/anthropic.ts` for every model, so a change of model does not change it). The health route reports which are present.
- Times are instants. The form sends them with the traveller's offset; the server rejects a time with no offset. `tz` is kept for display only.
- A round trip has an outbound and a return leg. The return begins at `turnaround` (an instant) when given, or at outbound arrival plus `stay` (minutes at the destination) when that is given instead; the two are exclusive. With neither, the split is the midpoint of the window. Arrival depends on the drive time, which only the route knows, so with a `stay` the outbound end and return start are null (`legsOf` in `src/lib/trip.ts`) until the corridor resolves them.
- A trip is active from the moment it is made until its end instant (`isActive` in `src/lib/trip.ts`). Only active trips are refreshed. An ended trip is never changed again but stays readable, with `status: "ended"`.
- Geocoding and routing use OpenStreetMap's public services: Nominatim to find places and name the towns along the road, and OSRM's demo server for the driving route (`src/lib/osm.ts`). Neither needs a key. They are meant for light use, so Nominatim requests are paced at one every 1.1 seconds and the app identifies itself in the user agent; set `OSM_CONTACT` to an email address or URL for that. Replace them with a keyed service if volume outgrows them.
- The corridor (`src/lib/corridor.ts`) is stored as `corridors/<id>` and built once per trip, only while the trip is active. The return leg of a round trip reuses the outbound road in reverse, and the corridor is where a `stay` becomes times: the destination is held from arrival for the stay and the return starts then. Towns are named every 50 km along the road and every 25 km within 100 km of each end (`samplePositions`), with the steps widened on very long routes; place names lose OpenStreetMap's legal-form prefix ("Town of Plattsburgh" becomes "Plattsburgh"). Passing times are the route's driving time spread evenly over its length, without traffic or stops, and the corridor says so in `sources.timing`; show them as estimates.
- Event sources (`src/lib/sources.ts`, `src/lib/anthropic.ts`) are found by Claude with web search, through Anthropic's official TypeScript SDK, from the corridor's stops in groups of five. A source is a listing page, never a single event, and records the stops it covers and whether it covers fixed activities (concerts, plays: a set start time), flexible ones (museums, parks: visited within opening hours), or both. The model's reply is built from web pages and is treated as untrusted: only https URLs on real hosts survive, with the query string removed, and only known kinds and stops that were asked about. The list is stored as `sources/<id>`, built once per active trip, and either every request succeeds or nothing is stored.
- Listings (`src/lib/listing.ts`, `src/lib/refresh.ts`) are what to do near each stop, read by Claude from the stop's sources for the times the traveller is there. Each is fixed (a concert or play: a start time and, if known, a length) or flexible (a museum or park: opening hours for each day, and a typical visit length if known). Claude's reply is untrusted and validated like the sources: https links, real instants with offsets, bounded text, known kinds, and a listing is kept only if it is on within three hours of a time the traveller is at that stop (`PASS_SLACK_MIN`). A listing's id is stable across refreshes, and for a flexible listing does not depend on its hours, so a pick or star made on it stays valid. They are stored as `listings/<id>`, one entry per place.
- Who reads the listings follows the Montreal board: a claude.ai routine (instructions in `docs/routine-prompt.md`, kept in the repository) posts them to `PUT /api/trips/<id>/listings`, which only the job token may call. `src/lib/ingest.ts` validates them exactly as a read made here is validated and follows the same rules: a place that comes back empty keeps its earlier listings, a place the traveller has passed is left alone, and a payload with no listings at all is refused. With `LISTINGS_BY=cron` the cron job reads the listings itself instead (`src/lib/listings-by.ts`).
- The refresh (`src/lib/pipeline.ts`, `GET` or `POST /api/refresh`) runs daily from Vercel Cron (`vercel.json`, 10:00 UTC) and only starts with the job token. For each trip that has not ended, soonest first, it builds the corridor and then the sources if they are missing, then, only when `LISTINGS_BY=cron`, reads the places that are due. An ended trip is never touched again, and a place the traveller has already passed is left alone. A place read within the last 20 hours is skipped. A read that fails or finds nothing never blanks the earlier listings. Work is bounded (three reads at once, twelve places per run, a deadline well inside the function limit), so a long route finishes over several runs; the response says what was left.
- The trip board (slice 5). `/` signs in and lists and makes trips (the form adds the browser's offset to each time, `src/lib/when.ts`); `/trips/<id>` is the board (`src/components/board-screen.tsx`). It reads everything in one request, `GET /api/trips/<id>/board`, and keeps the traveller's picks and stars in `plans/<id>` through `PUT /api/trips/<id>/plan` (`src/lib/plan.ts`): the whole plan is replaced each time, as the Montreal board's sync does, it is refused once the trip has ended, and it is deleted with the trip. What the board shows and how it plans is in `src/lib/board.ts`, which has no Node imports because it also runs in the browser. Listings are grouped by day in the trip's time zone, and a flexible listing appears under each day it is open while the traveller is there. The itinerary puts picks in time order, reports the gap between them, flags an overlap or a back to back, and places a flexible pick that has no chosen time at the earliest moment inside its opening hours that clears the picks already there, drive included; one that cannot be placed is said so. A drive time between two picks is the corridor's own estimate (the leg's duration spread over its distance, labelled with the routing service and "without traffic") and is shown only between stops on the same leg: across a round trip's stay it says nothing, in the way the Montreal board says nothing about where when it does not know. The look follows the Montreal board (its colour tokens are in `src/app/globals.css`, with the ink-3 grey darkened to meet contrast), and a category colour is never the only signal. Not yet built: a way to choose a time for a flexible pick (the plan format already allows one, `at`), and the installable app (slice 6).
- Canadian English in all user-facing text.
