# Plan

Road Trip follows the Montreal Weekend Board's model: a store of documents, a daily refresh that writes listings, and a board that reads them. The differences are that there are many boards (one per trip), each board covers a road and not a city, and a board stops being refreshed when its trip is over.

One slice per branch and pull request. Update this file when a slice answers an open question or changes a decision, and add the pull request to the slice when its number is known.

## Decisions and open questions

- Who reads the sources (slice 4). Superseded by slice 4b. The first reasoning was that a routine cannot be created per trip from inside the app, so a server-side job calling the Anthropic API was the default. That overlooked that one routine can loop over every active trip, as the Montreal board's does for its one board. The routine uses the account's routine allowance and not metered API billing, and keeping the two apps on the same mechanism makes code and prompts easier to share. Decided: the routine reads listings (instructions in `docs/routine-prompt.md`), and the cron job builds the corridor and sources and stays available as a fallback with `LISTINGS_BY=cron`. Sources are still found on the server, once per trip. Not yet measured: the routine allowance a daily run uses, and whether one run finishes all active trips. The routine's own instructions live in claude.ai, so a change is pasted in by hand. The routine reads web pages while it holds its token, so the token is its own (`ROUTINE_SECRET`) and reaches only the reads and the listings `PUT`, not the refresh token's reach.
- Settings shared with the Montreal board (slice 4b). The passcode setting is `BOARD_PASSCODE` in both apps. Remaining differences found by reading both repositories: the Montreal board's default model is `claude-sonnet-5` and Road Trip's is `claude-sonnet-5-5`; Montreal's record fields are `cat`, `free`, `note`, `when` and `hood` where Road Trip's are `category`, `cost`, `notes` and `schedule`; the Montreal board's gap between picks comes from neighbourhood and métro line, Road Trip's will come from drive times. Align record names before the trip board is built so that its code can be shared.
- Geocoding and routing (slice 2). Decided: OpenStreetMap's Nominatim and OSRM, which need no key but have usage policies meant for light use. Requests are paced and the app identifies itself. Replace with a keyed service if a trip count makes that unsuitable. The clients are covered by tests with stubbed replies and were also run once against the live services: a Montréal to Québec round trip with a one-night stay built in about 8 seconds and listed the towns on the Montréal to Québec autoroute in order.
- Schedule (slice 4). Daily on Vercel Cron, as the Montreal board runs daily. A trip made today should be refreshed once on creation so it is not empty until tomorrow.
- A listing is shown only if it falls in the window in which the traveller is passing that part of the road. The route's duration gives an estimate, and the estimate is labelled as one.
- Calling Claude (slice 3). Decided: the official `@anthropic-ai/sdk` with the `web_search_20260209` tool with server-side refusal fallbacks on. The model is `claude-sonnet-5-5` by default, chosen over Opus because the Montreal board works well on Sonnet and tokens cost half as much ($2 and $10 against $4 and $20 per million); `ANTHROPIC_MODEL` overrides it. Reasoning effort is pinned to medium for every model, because Sonnet 5.5 defaults to high and Opus 5.5 to medium, and an unpinned effort would let a change of model quietly change the reasoning spend. The Montreal evidence is for reading a poster image, so the choice is not yet compared on this work: run `LIVE_LISTINGS=1 npm run live` with each model. The cost of a trip scales with its number of stops. Each trip makes one request per five stops, run side by side, each limited to six searches. Not yet measured: the cost of a trip, and the quality of the sources found.
- Reading the sources (slice 4). Decided: one request per place, with the web search and web fetch tools, so the model reads the pages named for that place and may search for more there. A daily job reads each place once a day while the traveller has yet to pass it. Not yet measured: the cost of a refresh, which scales with the number of places, and how good the listings are. `LIVE_LISTINGS=1 npm run live` reads three places so both can be judged before the job is turned on. The schedule is `0 10 * * *` UTC, once a day like the Montreal board's refresh. Vercel's limits on cron frequency for the project's plan were not checked. The 300 second function limit set on the sources, listings and refresh routes has been accepted by Vercel's builds.
